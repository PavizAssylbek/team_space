# ADR 0001 — Минимальная frontend-архитектура Teamspace

Дата: 2026-10-10 (Asia/Aqtau).
Статус: принято для текущего каркаса.

## Контекст

Teamspace — учебный проект для перехода от frontend-разработки к Fullstack и
прикладному AI Engineering. Работа ведётся небольшими задачами с coding-агентом,
проверяемыми критериями и сохранением существующих пользовательских изменений.

На момент принятия решения нужна запускаемая стартовая страница с заголовком
«Teamspace». Список задач, backend и AI-функции будут реализовываться позже.
Проект использует FSD, но создание всех возможных слоёв заранее не требуется.

## Решение

### Стек

- React и TypeScript — основа frontend-приложения и существующего опыта пользователя.
- Vite — локальная разработка и production-сборка.
- pnpm — пакетный менеджер согласно `AGENTS.md`; версия `10.15.1` закреплена
  в `package.json`, зависимости зафиксированы в `pnpm-lock.yaml`.
- TypeScript с `strict: true` для приложения и конфигурации Vite.
- Oxlint — линтер, включённый в использованный официальный шаблон Vite.

### Структура исходников на момент настройки каркаса

```text
src/
├── main.tsx
├── app/
│   ├── App.tsx
│   └── styles.css
└── pages/
    └── home/
        ├── index.ts
        └── ui/
            └── HomePage.tsx
```

- `main.tsx` монтирует React в DOM и включает `StrictMode`.
- `app/App.tsx` собирает приложение; `app/styles.css` содержит глобальные стили.
- `pages/home/ui/HomePage.tsx` реализует стартовую страницу.
- `pages/home/index.ts` экспортирует страницу как её публичный API.
- Направление зависимости: `app` → `pages/home`; страница не импортирует `app`.

`pages/home` — текущая стартовая страница без отдельного роутера. Слой `pages`
определяет ответственность страницы и не требует установки библиотеки маршрутизации.

### Развитие FSD

Новые слои и сегменты создаются при появлении реальной ответственности:

- `entities/task/model` — доменные `Task` и `TaskStatus`.
- `entities/task/ui` — UI сущности, включая простой список задач через props.
- Страница связывает данные и отображение через публичный API сущности.
- `features` и `widgets` появляются при обоснованной самостоятельной функциональности.
- `shared` используется для кода без привязки к бизнес-сущности Teamspace.

При создании каркаса это было направлением следующего изменения. Реализованная
часть описана в дополнении о первом `TaskList` ниже.
Публичный API не отменяет ограничения на направление зависимостей FSD.

### Проверки

- `pnpm typecheck`: `tsc -b` проверяет приложение и конфигурацию Vite.
- `pnpm lint`: запускает Oxlint.
- `pnpm build`: проверяет TypeScript и создаёт production-сборку.
- Изменённые UI-сценарии проверяются в браузере.

Проверки каркаса прошли при его настройке; результаты записаны в
[PROGRESS.md](../../PROGRESS.md). Автоматизированные тесты, CI и техническая
проверка FSD-границ пока не настроены. Границы импортов проверяются ревью кода.

## Рассмотренные варианты

1. **Создать все слои FSD сразу.** Отложено: пустые папки не добавляют ответственности
   и затрудняют понимание маленького приложения.
2. **Оставить весь код в шаблонном App.tsx.** Выбрано разделение `app` / `pages`,
   чтобы с первого изменения было видно, где собирается приложение и где живёт страница.
3. **Сразу установить роутер, query-клиент и UI-библиотеку.** Отложено до появления
   маршрутов, асинхронных данных и повторяемых элементов интерфейса.

## Последствия

Каркас остаётся небольшим, а каждую новую зависимость и FSD-границу можно объяснить
конкретной задачей. Разработчик может проверить diff, типы, lint, сборку и UI.

По мере роста приложения потребуется принять дополнительные решения о маршрутизации,
получении данных, тестировании и обработке состояний. Их появление не следует
считать уже реализованной частью каркаса.

Пересмотреть решение при появлении нескольких маршрутов, HTTP API, повторяемых
бизнес-сценариев или когда текущие границы перестанут соответствовать ответственности кода.

## Реализация первого TaskList — 2026-10-10

Согласованное направление развития реализовано без новых зависимостей:

- `entities/task/model/types.ts` определяет `Task` и `TaskStatus`.
- `entities/task/ui/TaskList.tsx` отображает названия и статусы либо «Нет задач».
  Компонент получает `readonly Task[]`, не загружает данные и не меняет их.
- `entities/task/ui/task-list.css` содержит локальные стили списка.
- `entities/task/index.ts` экспортирует компонент и доменные типы.
- `pages/home/model/demo-tasks.ts` содержит демонстрационные данные.
- `pages/home/ui/HomePage.tsx` связывает данные с UI через публичный API сущности.

Направление импортов: `app` → `pages/home` → `entities/task`. Простой список
отображает одну бизнес-сущность, поэтому находится в `entities`; самостоятельного
пользовательского действия или композиции нескольких слайсов здесь пока нет.
`features`, `widgets` и `shared` для этой задачи не потребовались.

Пустой и непустой сценарии проверены в браузере, typecheck, lint и build прошли.
Результаты и ограничения проверок записаны в [PROGRESS.md](../../PROGRESS.md).

## Уточнение соглашений по запросу пользователя — 2026-10-10

- Для объектных контрактов используем `interface`: `Task` и `TaskListProps`.
  Для статусов — строковый `enum TaskStatus`. Алиасы `type` допускаются, только
  когда интерфейс или enum не выражает необходимый тип. Type-only imports/exports
  используются для интерфейсов; enum экспортируется и импортируется как значение.
- В `tsconfig.app.json` установлен `erasableSyntaxOnly: false`, поскольку обычный
  enum требует преобразования в JavaScript. Его выполняет Vite. `strict` и остальные
  проверки сохранены; `tsconfig.node.json` не менялся.
- Все исходные стили переведены в SCSS Modules: `App.module.scss`,
  `HomePage.module.scss` и `TaskList.module.scss`. Глобальными оставлены только
  явно обозначенные `:global(:root)` / `:global(body)` для базового оформления.
  Заголовок страницы и элементы списка используют локальные классы через `styles`.
- Для SCSS добавлен Sass как единственная новая прямая devDependency.
- Алиас `@/` указывает на `src`: `paths` в TypeScript и `resolve.alias` в Vite.
  Импорты между слайсами по-прежнему проходят через публичные API. Относительные
  пути ограничены двумя `../`; алиас не меняет направление зависимостей FSD.

Предыдущие разделы фиксируют этапы реализации; актуальные правила закреплены
в `AGENTS.md`, а актуальная структура приведена в README.
Typecheck, lint, production-сборка и оба состояния списка повторно проверены.
В браузере также подтверждено, что локальный `.title` страницы и задачи получает
разные имена классов. Результаты записаны в [PROGRESS.md](../../PROGRESS.md).

## Именование и папки UI-компонентов — 2026-10-10

По запросу пользователя исходные файлы и папки используют kebab-case, а имена
React-компонентов, интерфейсов и enum сохраняют PascalCase. Канонические имена
документов и служебных файлов не переименовываются.

Внутри `ui` каждый компонент находится в своей папке. Для одного компонента
используем `index.tsx` и `index.module.scss`; для нескольких связанных компонентов
допускаются описательные kebab-case имена с публичным `index.ts`.

Актуальные пути:

- `app/index.tsx` и `app/index.module.scss` — композиция приложения и базовые стили.
- `pages/home/ui/home-page/index.tsx` и `index.module.scss` — стартовая страница.
- `entities/task/ui/task-list/index.tsx` и `index.module.scss` — список задач.

Публичные API слайсов сохранены; внутрислайсовые импорты после переноса используют
максимум два `../`. Поведение и зависимости не менялись. Typecheck, lint и build
повторно прошли. Подключение готового UI-kit остаётся отдельным следующим решением.

## Подключение Mantine — 2026-10-10

Пользователь выбрал готовый UI-kit Mantine. Установлены только `@mantine/core`
и `@mantine/hooks` версии `9.7.1`; версии совместимы с текущим React.

- Один `MantineProvider` расположен в `app/index.tsx`. Пока приложение использует
  светлую тему (`forceColorScheme="light"`), соответствующую текущим стилям списка.
- Там же подключён `@mantine/core/styles.layer.css`. Библиотечные стили находятся
  в слое `mantine`; собственные SCSS Modules без слоя сохраняют приоритет.
- Базовые шрифт, цвет и фон перенесены с `:root` на `body`, поскольку Mantine также
  задаёт базовое оформление непосредственно на `body`.
- Страница использует `Title` с `order={1}` / `order={2}`, сохраняя заголовки `h1` / `h2`.
- TaskList, его props, модель и данные не изменены. Обёртки в `shared/ui` пока не нужны.
- PostCSS-пресет не добавлен: готовые стили Mantine и обычные SCSS Modules работают
  с уже установленным Sass. Специальные PostCSS-функции и миксины пока не используются.

Установка по lockfile, typecheck, lint и production-сборка прошли. В браузере
проверены подключение стилей и провайдера, заголовки, фон и цвет текста, а также
пустой и непустой TaskList; ошибок и предупреждений в консоли нет.
Фильтрация по статусу остаётся следующей отдельной задачей.

Источники: [Mantine с Vite](https://mantine.dev/guides/vite/),
[CSS layers](https://mantine.dev/styles/mantine-styles/),
[необязательный PostCSS-пресет](https://mantine.dev/styles/postcss-preset/).

## Фильтрация задач по статусу — 2026-10-10

- Новый слайс `features/task-filter-status` содержит пользовательское действие:
  управляемый `TaskStatusFilter` и чистую функцию `filterTasksByStatus`.
  Оба экспортируются через публичный API фичи.
- Для четырёх фиксированных вариантов используется готовый Mantine `NativeSelect`
  с видимой подписью «Статус задачи». Собственное оформление — SCSS Module
  внутри `ui/task-status-filter/`.
- `pages/home` хранит только выбранный статус, вычисляет видимые задачи и связывает
  фильтр с TaskList. Дополнительный store, widget и мемоизация не требуются.
- `TaskStatus | null` описывает состояние фильтра: `null` означает «Все».
  Это не доменный статус задачи, поэтому enum `TaskStatus` не расширяется.
  Пустое значение native select преобразуется в `null` через проверенную опцию,
  без приведения произвольной строки к enum.
- Подписи статусов вынесены из TaskList в `entities/task/model/status-labels.ts`
  и экспортируются через API сущности. `Readonly<Record<TaskStatus, string>>`
  обеспечивает полноту подписей; список и фильтр используют один словарь.
- TaskList получает уже отфильтрованный массив и сохраняет пустое состояние
  «Нет задач». Исходные данные не меняются; «Все» возвращает исходный массив.

Направление зависимостей: `pages/home` → `features/task-filter-status` →
`entities/task`; страница также напрямую использует TaskList через API сущности.
Новые зависимости и настройки сборки не потребовались.

Typecheck, lint и production-сборка прошли. В браузере проверены все статусы,
восстановление списка и пустой результат на временном наборе замороженных данных.
Постоянная тестовая инфраструктура пока отсутствует. Подробности:
[PROGRESS.md](../../PROGRESS.md).

## Компоненты Mantine в TaskList — 2026-10-10

TaskList использует `Box component="ul"`, `Paper component="li"`, `Group` и `Text`.
Так сохраняется семантика списка, а оформление строк и типографика задаются Mantine.
Пустое состояние также использует Text. SCSS Module сохраняет раскладку списка
и перенос длинного названия; дублирующие фон, граница и отступы строки удалены.
Размещение в `entities/task`, props, данные и логика фильтрации сохранены.
